# JudicialGPT — Family Law Agent API

A RAG-backed REST API for Pakistan family law legal research and judgment
drafting. Built with FastAPI, LangChain, Google Gemini, and FAISS.

This document is for **frontend developers** integrating with the API —
it does not cover ingestion or agent internals.

---

## 1. Base URL

```
http://localhost:7007
```

Change the host/port to wherever the API is deployed.

Interactive Swagger docs are auto-generated by FastAPI and available at:

```
http://localhost:7007/docs
```

---

## 2. Authentication

None at the API layer currently. If this is deployed publicly, put it
behind a gateway/reverse proxy that handles auth — don't expose it
directly to the internet as-is.

---

## 3. Core Concept: Sessions

Every conversation is scoped to a `session_id` string that **you**
provide. This is how the agent keeps context across follow-up
questions (e.g. "What about custody?" after asking about dissolution).

- Use one `session_id` per case/conversation in your UI — e.g. a case
  number, or a UUID you generate when a new chat starts.
- Sessions live **in server memory only**. They are lost on server
  restart. There is no persistence layer — if you need chat history to
  survive restarts, your frontend/backend should store the Q&A pairs
  separately.
- The server automatically trims each session to the last 5 exchanges
  (configurable server-side) — you don't need to manage trimming.

## 4. Endpoints

### `GET /health`

Liveness/readiness check. Call this on app startup to confirm the
agent has finished loading (model + embeddings + vector index can take
a few seconds to a minute to load on server boot).

**Response `200`**
```json
{
  "status": "ok",
  "model": "gemini-3.6-flash"
}
```

**Response `503`** — agent still initialising, retry shortly.

---

### `POST /ask`

The main endpoint. Submit a question or instruction; get back an
answer plus the statute passages that informed it.

**Request body**
```json
{
  "query": "What are the grounds for judicial dissolution of marriage under the Dissolution of Muslim Marriages Act 1939?",
  "session_id": "case_2026_family_101"
}
```

| Field        | Type   | Required | Notes                                                                 |
|--------------|--------|----------|------------------------------------------------------------------------|
| `query`      | string | yes      | Min length 1. The question or drafting instruction.                   |
| `session_id` | string | no       | Defaults to `"default"`. Use a unique ID per case/chat in production. |

**Response `200`**
```json
{
  "answer": "Under Section 2 of the Dissolution of Muslim Marriages Act 1939, a woman married under Muslim law may obtain a decree for dissolution of her marriage on any of the following grounds: (a) the whereabouts of the husband have not been known for a period of four years; (b) the husband has neglected or failed to provide for her maintenance for two years; ...",
  "sources": [
    {
      "file": "Dissolution of Muslim Marriages Act 1939.pdf",
      "page": 2,
      "snippet": "Section 2. Grounds for decree for dissolution of marriage. A woman married under Muslim law shall be entitled to obtain a decree…"
    }
  ],
  "session_id": "case_2026_family_101"
}
```

| Field               | Type   | Notes                                                              |
|---------------------|--------|----------------------------------------------------------------------|
| `answer`             | string | The agent's response. May include Markdown-style formatting.       |
| `sources`            | array  | Retrieved statute passages that grounded the answer. Can be empty. |
| `sources[].file`     | string | Source PDF filename.                                               |
| `sources[].page`     | string \| int | Page number within that PDF (`"N/A"` if unavailable).       |
| `sources[].snippet`  | string | First ~200 characters of the retrieved chunk, for citation display.|
| `session_id`         | string | Echoes back the session ID used, for convenience.                  |

**Response `500`**
```json
{ "detail": "Agent error: <message>" }
```
Surface this as a generic "something went wrong, please retry" in the UI —
don't show raw error text to end users.

**Response `503`** — agent not ready yet (see `/health`).

> **Latency note:** this endpoint calls an LLM and does vector search, so
> expect responses in the **few-second range**, not milliseconds. Show a
> loading/typing indicator in the UI rather than a blocking spinner with
> no feedback.

---

### `POST /sessions/{session_id}/clear`

Clears a session's conversation memory (e.g. the judge starts a new
case) without deleting anything server-side beyond that in-memory
history. Functionally identical to `DELETE /sessions/{session_id}`.

**Response `200`**
```json
{ "session_id": "case_2026_family_101", "status": "cleared" }
```

---

### `DELETE /sessions/{session_id}`

Same effect as `/clear` above — provided as a REST-conventional
alias. Use whichever fits your frontend's HTTP client patterns better.

**Response `200`**
```json
{ "session_id": "case_2026_family_101", "status": "deleted" }
```

---

### `GET /sessions`

Lists all currently active sessions in server memory, with how many
Q&A exchanges each has. Useful for an admin/debug view — not typically
needed in the main judge-facing UI.

**Response `200`**
```json
{
  "sessions": [
    { "session_id": "case_2026_family_101", "exchanges": 4 },
    { "session_id": "case_2026_family_102", "exchanges": 1 }
  ]
}
```

## 5. Typical Frontend Flow

1. On app load: `GET /health` — if `503`, poll every few seconds until `200`.
2. When a new case/chat is opened: generate a `session_id` (e.g. `crypto.randomUUID()` or your case number) and keep it in your app state.
3. On each user message: `POST /ask` with `{ query, session_id }`, show `answer`, optionally render `sources` as expandable citations.
4. When the user starts a new case in the same UI session: call `/sessions/{session_id}/clear`, then start fresh with a new `session_id`.

### Minimal `fetch` example

```javascript
async function askJudicialGPT(query, sessionId) {
  const res = await fetch("http://localhost:7007/ask", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ query, session_id: sessionId }),
  });

  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    throw new Error(err.detail || `Request failed: ${res.status}`);
  }

  return res.json(); // { answer, sources, session_id }
}
```

## 6. Things to Watch For

- **Cold start**: the very first request after server boot loads the
  LLM client, embedding model, and FAISS index — this can take a
  while. Always check `/health` before enabling the chat input.
- **CORS**: currently wide open (`allow_origins=["*"]`) for local dev.
  This will be locked down before production — coordinate with backend
  if requests start getting blocked after deployment.
- **No streaming**: `/ask` returns the full answer in one response,
  not a token stream. Build the UI around a "wait then show" pattern,
  not incremental text rendering.
- **No persistence**: don't rely on `/sessions` or session memory
  surviving a server restart or redeploy.
- **`sources` can be empty**: not every answer will have retrieved
  passages (the agent can answer from general legal knowledge too) —
  handle an empty `sources` array gracefully in the UI rather than
  assuming citations always exist.
